# SteelIQ – Lateral Enterprises

## Overview
SteelIQ is a professional quotation and estimating platform designed for the window and door industry. Its primary purpose is to automate and optimize the quotation workflow, offering features such as item configuration, real-time visual representation through SVG drawings, precise pricing, and efficient document generation. The platform provides comprehensive estimate and quote lifecycle management, detailed pricing breakdowns, and a flexible template-driven PDF engine. It supports organizational and division-specific settings, dynamic specification displays, and a project-centric CRM workflow, all aimed at enhancing accuracy and streamlining operations. SteelIQ also supports a complete quote workflow for the Laser division, including manual item entry, snapshot persistence, and domain-specific rendering with a dedicated pricing engine.

## System Architecture
**Frontend**: Built with React and TypeScript, leveraging Shadcn UI for a responsive, mobile-first user experience.
**Backend**: Developed using Express.js, with a PostgreSQL database managed via Drizzle ORM and node-postgres.
**Drawing Engine**: Utilizes SVG for real-time technical drawing rendering, with server-side SVG to PNG conversion for export without a browser DOM.
**State Management**: React state manages UI components, while TanStack Query handles API data fetching and caching. Global settings are managed with React Context and localStorage.
**Routing**: Client-side navigation is managed by Wouter with a centralized route helper.
**Export Capabilities**: Supports SVG to PNG conversion and multi-page, vector-text selectable PDF generation using jsPDF.
**Storage**: Item photos and drawing PNGs are stored in PostgreSQL (`bytea`), with an in-memory cache and filesystem mirror. Division logos are stored as base64 data URLs in PostgreSQL.
**Multi-Division Architecture**: Supports organizational and division-specific settings, including `domainType` for conditional UI behavior and domain-aware contracts.
**Spec Dictionary System**: Provides configurable entries for dynamic display and override of specifications.
**Laser Division Workflow**: Supports a complete quote workflow, including manual item entry, snapshot persistence, domain-specific preview and PDF rendering, a detailed sheet materials library, a separate time-based process costing engine, and a system for manual pricing overrides and provisional lines. Pricing profiles are versioned, and a 4-tier precedence model determines pricing. Laser line items can include attached manual procedures, which are displayed as nested sub-rows.
**Quote Management**: Features a comprehensive lifecycle (Draft, Review, Sent, Accepted/Declined, Archived) with atomic sequential numbering, immutable revision history, and server-side status enforcement. Each quote includes an `EstimateSnapshot` for immutable revision data.
**Pricing System**: Calculates material, labor, glass, liner, and handle costs, providing net cost, sale price, and margin. Supports manual price override, fees, markup application, GOS charges, and geometry-aware pricing.
**Master Library Systems**: Centralized libraries for direct materials, manufacturing labor, installation labor, and delivery methods, with controls for active status and default designations.
**CRM Workflow**: Project-centric CRM with automatic customer linking from quotes, project creation linked to quotes, and sub-query endpoints. Projects have auto-assigned `projectNumber`. Accepted Laser division quotes auto-match or auto-create CRM customers and include a 4-step delivery workflow. A 7-stage workflow strip (Estimate → Quote → Accepted → Customer → Project → Job → Invoice) is integrated across detail pages.
**Invoice Management**: Manages invoices with detailed line items, full CRUD operations, automated status demotion, and Xero integration.
**UI/UX**: Features responsive tables, polished spec row formatting in PDFs, project dashboard guidance, customer relink safeguards, and an enterprise app shell with workflow-domain grouped navigation. Standardized list page headers, row styling, and `max-w-7xl` width for settings/users pages. Governance systems support archive/delete with chain-aware safety guards, and audit activity tables use business-facing identifiers.

**LL Production Allowance Tiers (Phase 5H.3)**: Internal-only, additive extension of the LL pricing engine. `LLPricingSettings` gained an optional `productionAllowanceTiers?: LLProductionAllowanceTier[]` JSONB field (no SQL migration). Each tier specifies a quantity band (`minQty`/`maxQty`, optional `minSheets`/`maxSheets`) and adds **fixed batch setup + per-sheet handling + per-part touch time (capped) + QA/packing** minutes plus a **production overhead %** applied to `sellBeforeAllowanceAndOverhead`. Selected tier is highest-`minQty` match against the line's `safeQty` and `estimatedSheets`. Engine formula: `allowanceMin = fixedBatch + sheets·perSheet + min(qty·perPartSec/60, cap) + qaPacking`; `allowanceBuy = allowanceMin/60 · operatorRate`; `allowanceSell = allowanceMin/60 · shopRate`; `overhead = sellBefore · pct/100`. Totals now include both. Profiles with no tiers behave bit-identical to pre-5H.3. Same release also corrected **material under-allocation**: when `partsPerSheet > 0` the engine now charges whole sheets (`estimatedSheets · pricePerSheetExGst`), matching supplier invoicing. The internal Pricing Breakdown panel in the LL builder surfaces a `Production Allowance` block with tier badge, minutes detail, allowance Buy/Sell/Margin row, overhead row, and an amber review-required notice when `safeQty >= reviewRequiredAboveQty`. Pricing-profile admin gained a tier editor (seed-defaults button + per-tier fields + gap/overlap coverage warnings) and a read-only viewer table. **Customer Preview, customer PDF, LJ, LE, child operation formulas, and snapshot schema are unchanged** — allowance and overhead are surfaced internally only and do not appear in any customer-facing surface.

**LL Material Allocation Modes (Phase 5H.9A)**: Internal-only, legacy-safe extension of the LL material costing block. Each laser line gained three optional fields (`materialAllocationMode`, `yieldMinimumSheetChargePercent`, `recoverableRemnantPercent`) and `LLPricingSettings` gained matching profile-default seeds (`defaultMaterialAllocationMode` etc.). **CRITICAL legacy-safety contract**: the engine (`computeLLPricing` in `client/src/lib/ll-pricing.ts`) resolves an undefined/missing `materialAllocationMode` to **`whole-sheets`** and NEVER falls back to the profile default — profile defaults only seed brand-new line items in the builder (`makeEmptyItem`), and `openEditDialog` preserves stored line values without profile substitution. Two modes: **whole-sheets** (legacy — `materialBuyCost = estimatedSheets × pricePerSheetExGst`, bit-identical to 5H.3) and **yield-based** (single-sheet only: `usage = qty/partsPerSheet`; `nonRecoverable = 1 − recoverableRemnantFraction`; `allocated = max(usage, minSheetChargeFraction, nonRecoverable)`; `buy = pricePerSheetExGst × allocated` on a one-sheet basis with no `× estimatedSheets` double-count; `sell = buy × (1 + materialMarkup)`). Multi-sheet yield jobs (`estimatedSheets > 1`) preserve whole-sheet allocation and set `yieldMultiSheetFallback` for the internal breakdown (true multi-sheet yield is ambiguous without real nest geometry). Defaults: `minSheetCharge = 25%`, `recoverableRemnant = 75%`. Profile create/duplicate (`POST /api/ll-pricing-profiles`) seeds the three `default*` fields (mode → `whole-sheets`) so activating a new profile never changes existing quoting. UI is **internal-only**: a Material Allocation section in the Add/Edit Item modal (mode Select + yield inputs + calculated allocated % + multi-sheet fallback notice) and an expanded Material breakdown detail card (allocation-mode badge + yield breakdown rows). **No customer Preview, customer PDF, snapshot schema, LJ, or LE changes.** Benchmark anchors (active profile, no manual edit, must stay within $0.01): **LL-EST-0036 ≈ $16,868.63 ex GST** and **LL-EST-0037 ≈ $920.04 ex GST** — both carry no stored allocation mode so they resolve to whole-sheets and remain invariant.
